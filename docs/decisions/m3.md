# M3: Catalog and TMDB — historical decisions and implementation notes

This preserves the milestone notes as recorded before they were moved out of the plan. Their branch and review statuses are historical; see the [rewrite plan](../rewrite-plan.md) for current status.

## Original scope and completion criterion

- Tables: `movies`, `shows`, `seasons`, `episodes`, `provider_cache`, `jobs`.
- TMDB provider with caching and rate limiting; search and detail endpoints.
- Upsert movies, shows, seasons, and episodes by external ID, with episodes anchored on TMDB episode ID.
- TMDB attribution: logo and notice on the About page, a short credit in the footer; optional image cache.
- Job worker and scheduler, with a metadata refresh job, and a job that deletes expired sessions (moved from login, where M2 left it).
- **Done when:** you can search for a title and open its detail page.

## Historical notes

- **Status: done** (2026-11-03), except the optional image cache, which is a later slice or moves to M6. Built in slices: (1) the `jobs` table, worker, and scheduler, with expired-session cleanup moved into a job; (2) the `provider_cache` table and the shared provider HTTP client; (3) the TMDB adapter, tested against fixtures; (4) the catalog tables and upserts, and the metadata refresh job (split into 4a and 4b below); (5) search and detail endpoints; (6) the SPA's search and detail pages and the TMDB attribution. The optional image cache is a later slice or moves to M6.
  - Slice 1 is merged (#21): `jobs` (migration 00004), `internal/jobs` with one worker and an interval scheduler, retention, crash recovery, and the hourly `session_cleanup` job, which login no longer does. Decisions made while building it:
    - The `jobs_maintenance` job that prunes finished jobs is internal to `internal/jobs` and scheduled daily; it keeps done jobs 7 days and failed ones 30, and like every scheduled job also runs at startup.
    - A job left `running` by a crash counts as an attempt when startup puts it back in the queue, and fails instead if that was its last attempt, so a job that kills the process can't crash-loop the server. One cut short by a clean shutdown does not count; the claim and that requeue use a context detached from the cancelled one, so shutdown can't leave a row `running`. If a run's outcome can't be written, the worker recovers the row the same way before its next claim.
    - The server binds its port before the queue starts, so a second `watcht serve` on the same data fails before it can requeue the running server's jobs. The outcome updates only change rows still `running`.
    - `last_error` keeps at most 2000 bytes, cut on a rune boundary; a successful run clears it. An unknown kind fails immediately; a recovered panic is handled as an ordinary error, so it uses the next attempt.
    - The worker and the scheduler each check every 5 seconds, and `Enqueue` wakes the worker; both are internal constants, not settings.
  - Decided by the maintainer (2026-10-28):
  - TMDB API key: the `WATCHT_TMDB_API_KEY` environment variable for now; an admin settings page may replace or override it later. Without a key the server still starts, and catalog endpoints return a clear "not configured" error.
  - Detail pages and their API use the TMDB ID (`/movies/603` is TMDB movie 603), so opening a search result fetches and upserts it with no extra step, and URLs survive a reinstall. This is an exception to "user-facing IDs are the internal integers" for catalog items; internal IDs stay internal (joins, watch events).
  - Metadata refresh: an item is refreshed when its metadata is older than its cache lifetime and its detail page was opened in the last 30 days (a `last_viewed_at` column). M4 adds "watched recently" to the same rule.
  - TMDB client: a token bucket at 20 requests a second (TMDB allows about 40), retrying 429s after `Retry-After`. Cache lifetimes: search 1 day; movies and ended shows 7 days; ongoing shows and seasons 1 day; external ID lookups 30 days. Raise them later if needed.
  - Slice 2 is merged (#22): `provider_cache` (migration 00005), the shared client in `internal/providers`, and the daily `provider_cache_prune` job. No provider is constructed in `cmd/watcht` yet; slice 3 adds the first. Decisions made while building it:
    - A `ttl` of 0 turns the cache off for that call, stale fallback included. Only a 200 with a body that is valid JSON and decodes into the caller's value is stored; another 2xx code is a `StatusError`, not a success. A fresh entry that no longer decodes (the adapter's type changed) is fetched again into a zeroed value, so nothing from the old entry leaks into the result.
    - Retries are for 429, 502, 503, 504, and transport errors, at most three attempts in all. A 429 waits for `Retry-After` (seconds or an HTTP date), up to 30 seconds; a longer wait, or a number too large to read, fails at once without a retry. Other retries wait 0.5 s, then 1 s. Only a 429 honours `Retry-After`; a 503 with one is retried on the normal schedule.
    - The stale fallback covers transport errors and 5xx responses after the retries. It never covers a 4xx, including a 429 that ran out of retries.
    - Redirects are not followed; a 3xx is a `StatusError`. A redirect would send the key header to another host.
    - The rate limit is one token bucket per client that every attempt takes. A wait the context cuts short gives its token back (waits already handed out to others don't shrink, so the refund is approximate). The bucket always runs on the real clock, not the client's `Now`: an adapter's tests with a fixed `Now` would otherwise never refill it.
    - A path containing `?` or `#` is refused before any request, since a key pushed into it would be stored or logged.
    - Error and log text never carries header values, the query, or the body. `encoding/json`'s own messages can quote a number from the body (an overflowing one, for instance), so a decode error names only the field and the Go type.
    - The cache key is the path, then `?` and `url.Values.Encode()`. Values under one key keep their order in the key and in the request.
    - The timeout applies to each attempt, body read included. A body over 8 MiB is an error and is never cached in part.
    - The `provider_cache_prune` job runs daily and at startup, like `jobs_maintenance`. It deletes entries that expired more than 30 days ago, for every provider; an entry exactly 30 days past expiry is kept.
    - `providers.New` panics on a missing provider name, or on a BaseURL that isn't an absolute http or https URL with no credentials, query, or fragment. Those are wiring bugs, so they fail at startup.
  - Slice 3 is merged (#23): `internal/providers/tmdb` (search, movie, show, season, episode, and IMDb/TVDB lookups through the shared client), `WATCHT_TMDB_API_KEY` in config, and recorded fixtures in its `testdata/`. Nothing constructs the adapter yet; slice 5's endpoints are the first user, and startup logs one line when the token is missing. Decisions made while building it:
    - Search uses TMDB's multi search, so one request returns movies and shows together; people are dropped, so a page can hold fewer than 20 results. `include_adult=false`.
    - The token is TMDB's v4 API Read Access Token, sent as `Authorization: Bearer`.
    - Every show is cached for 1 day: the cache lifetime is chosen before the response says whether the show has ended. The 7-day lifetime for ended shows is applied by slice 4's refresh rule, from stored data.
    - A season's episodes take their show ID and season number from the request, not the response. A show counts as ended when its status is `Ended` or `Canceled`.
    - Arguments are checked before any request: IDs above 0, season 0 or more (0 is specials), episode 1 or more, page 1–500 (below 1 means 1), a non-empty trimmed query, and an IMDb ID matching `tt` plus 7–10 digits, since it goes into the path. A failure is `tmdb.ErrInvalidArgument` and never echoes the value.
    - Dates are `YYYY-MM-DD` strings, empty when TMDB has none or sends an invalid one. Image fields keep TMDB's paths, not full URLs.
  - Slice 4 is split in two: (4a) the catalog tables, the upserts, and syncing a whole show; (4b) the job that fetches a new show's episodes, `last_viewed_at`, and the metadata refresh job. Decided by the maintainer (2026-10-31):
    - Opening a show stores the show and its season list from one request. A background job (4b) then fetches every season's episodes, so the page doesn't wait on a request per season.
    - An episode or season that TMDB stops listing is kept, since watch history points at it, and gets a `missing_since` time. It's hidden from season lists and progress, and comes back if TMDB lists it again.
    - Only `tmdb_id` is unique. `imdb_id` and `tvdb_id` get plain indexes, because TMDB sometimes has two entries with the same IMDb or TVDB ID, and that mustn't stop a title from being stored. Imports (M5) send more than one match to review. `trakt_id` arrives with M5.
    - Genres are a `genres` table (TMDB genre ID and name) with `movie_genres` and `show_genres` join tables.
  - Slice 4a is merged (#24): migration 00006 (`genres`, `movies`, `shows`, `movie_genres`, `show_genres`, `seasons`, `episodes`) and `internal/catalog`, which stores TMDB data (`UpsertMovie`, `UpsertShow`, `UpsertSeason`, `FetchMovie`, `FetchShow`, `SyncShow`) and reads it back by TMDB ID. Nothing calls it yet. Decisions made while building it:
    - Each upsert is one write transaction, and no TMDB call is made while one is open: the single write connection would deadlock with the client's cache write.
    - An episode is matched only by its TMDB ID, so a renumbering or a move to another season or show keeps its row. An episode that its season's latest response doesn't list gets `missing_since` at once, not only after a full refresh, so a moved episode never shows twice. It's cleared when the season it moved to is stored, so the order seasons are fetched in doesn't matter.
    - `tmdb_id` must be above 0 everywhere, so a row TMDB sent without an ID can't merge unrelated episodes. Season and episode numbers have plain indexes, not unique ones, so a renumbering that swaps two episodes can't fail halfway.
    - If TMDB's season list repeats a number, `SeasonEpisodes` reads the season with the lowest TMDB ID (see `docs/TECH_DEBT.md`).
    - A season response has no episode IMDb or TVDB IDs, so storing a season leaves those columns alone instead of clearing them. Nothing fills them yet; M5's import matching needs a source (the episode endpoint returns them).
    - A season's episode count is TMDB's count from the show's season list, not the number of episodes stored. `episodes_updated_at` stays empty until a season's episodes have been stored, which tells "not fetched yet" apart from "no episodes".
    - For M4: when a whole season goes missing, its episodes aren't marked themselves. Progress and stats queries must also check `seasons.missing_since`, and `seasons.not_found_since` (added in 4b).
  - Slice 4b is merged (#25): migration 00007 (`last_viewed_at` on movies and shows, `not_found_since` on seasons), `MarkMovieViewed`/`MarkShowViewed`, the `catalog_sync_show` job that fetches a newly stored show's episodes, and the hourly `catalog_refresh` job, wired in `cmd/watcht` only when `WATCHT_TMDB_API_KEY` is set. Decided by the maintainer (2026-10-31):
    - A season that TMDB lists but returns 404 for gets a separate `not_found_since` mark and the sync carries on with the other seasons. It's hidden like a missing season, but the show's season list doesn't clear the mark (the list still includes it); only a successful fetch of that season does. A full show sync retries it once per show lifetime.
    - Refresh calls never use the provider client's stale fallback (`providers.WithoutStale`): during a TMDB outage the run stops and retries with backoff, instead of storing old data as freshly updated. Page loads keep the fallback.
  - Decisions made while building it:
    - A show refresh is a full `SyncShow`, so seasons follow their show's lifetime. A viewed show is due when its own metadata or any of its visible seasons (not missing or not found) is older than its lifetime, or a season's episodes were never fetched, so a sync that failed partway is picked up on the next run.
    - Each run handles at most 50 movies and 10 shows, oldest first, so it fits the 5-minute job timeout at 20 requests a second.
    - A title TMDB returns 404 for is kept (history may point at it), and its metadata time is moved so it sorts last. A movie is then asked for again after its 7-day lifetime; a show is asked for again on each run once its seasons are past their lifetime, while it's viewed.
    - Opening a page marks it viewed at most once an hour. The sync job is queued after the show's write commits, with a context that survives the client disconnecting, and a unique key so a second open doesn't queue it twice.
    - Slice 5's handlers need the catalog service, but the router is built before the job queue starts (the port is bound first). Slice 5 splits building the queue and the catalog from starting the queue.

  - Slice 5 is merged (#26): `GET /api/v1/search`, `/movies/{id}`, `/shows/{id}`, and `/shows/{id}/seasons/{number}` in `internal/httpapi/catalog.go` (`/shows/{id}/episodes` added in UI pass part 2), behind `withUser`; `buildJobs` in `cmd/watcht` builds the queue, TMDB client, and catalog without starting the queue, so the router gets them before the port is bound; `providers.Unavailable`; the TypeScript types and `web/src/lib/api/catalog.ts`. Decided by the maintainer (2026-11-02):
    - A season whose episodes the background job hasn't fetched yet (`episodes_updated_at` is empty) returns 200 with `"episodes_pending": true` and `"episodes": null`. Each season in the show response carries `episodes_pending` too.
    - Without `WATCHT_TMDB_API_KEY`, all four routes return 503 `tmdb_not_configured`, checked after authentication, so a signed-out request is still 401.
    - Search results use `"show"` for TMDB's `"tv"`, matching the routes.
  - Decisions made while building it:
    - A detail page reads stored data and fetches from TMDB only for a title that isn't stored, then marks it viewed; a failed view write is logged and the page is still served. The season endpoint never fetches: it's 404 for a show that isn't stored, so the SPA opens the show first. Reading a season marks its show viewed.
    - Search trims the query and collapses runs of whitespace, then allows 1 to 100 characters (runes); `page` is 1 to 500. Path IDs are base-10 integers that fit TMDB's signed 32-bit IDs (show and movie IDs 1 or more, season numbers 0 or more); anything else is 404 with no TMDB request.
    - Errors: not found (stored or at TMDB) is 404 `not_found`. Any provider failure, meaning a status error (TMDB's 401 for a bad token included), a transport failure, or an unusable body, is 502 `provider_unavailable` and is logged; the provider client's errors never carry the query or headers. Anything else is a 500. A request the client cancelled gets no response body.
  - Accepted risks from the slice 5 review (2026-11-02), not fixed:
    - A first fetch can still be served the client's stale fallback (only if an earlier fetch succeeded but its upsert failed), and is then stored as fresh. Page loads keep the fallback, as decided in 4b.
    - Every distinct query and page is a `provider_cache` row kept about 31 days. The 100-character cap, sign-in, and the rate limit bound it.
    - TMDB 404s aren't cached, so each request for a missing ID costs a TMDB request.
    - A rejected token (TMDB's 401) is a 502 that says to try again later, and every request logs an error. A separate code or a hint to check `WATCHT_TMDB_API_KEY` can come with the admin settings page.
    - The GET routes write (fetching and storing a title, marking it viewed), and GETs pass the cross-origin check, so another site can make a signed-in browser store a title. No user data changes.
  - Slice 6 is merged (#27): the SPA's search overlay and `/search`, `/movies/[id]`, `/shows/[id]` with seasons and episodes, `/about`, the footer with a TMDB credit, and `DESIGN.md`. Decided by the maintainer (2026-11-02):
    - The API returns image URLs (`poster_url` w342, `backdrop_url` w1280, `still_url` w300) next to the TMDB paths, built by one helper in `internal/httpapi` so the optional image cache only changes that helper. The frontend never builds TMDB URLs.
    - Visual checks use the recorded fixtures, not live TMDB: `scripts/fake-tmdb` (`make fake-tmdb`) and `WATCHT_TMDB_BASE_URL` (development only, https unless loopback), always with a throwaway data directory, since the fake's cache rows and not-found marks would carry over into real use. `make dev` still talks to TMDB unless you set the variable yourself.
    - Look: the classic Trakt layout, in the "Woodland Fire" palette (pine and sage with a burnt orange accent), with a derived light theme. `DESIGN.md` at the repository root holds the system that M4's pages follow.
    - Navigation: a top nav on desktop, no sidebar. Settings, Users, and About are in the user menu. On phones, navigation and search go at the bottom (a tab bar: Dashboard, Search, History, Watchlist, More) and page controls stay at the top, as modern phone apps do. The tab bar is built in M4, once there's more than one destination; until then phones get a slim header with search and menu buttons.
    - Search is an overlay over the blurred page (opened from the header or `/`), with a full-page `/search?q=` for links and Back.
    - A show's seasons and episodes are on its page, picked with `?season=N`. A season whose episodes aren't fetched yet polls every 3 seconds, for up to 2 minutes.
    - The TMDB logo is TMDB's official "Alt short" SVG, unedited, drawn as a mask in pure black (light theme) or white (dark theme), which TMDB's rules allow. It and the full notice are on the About page only; the footer has a short "data from TMDB" credit with a link, like Letterboxd. This footer is a placeholder: a full one, with all its links and logos, comes later.
  - Decisions made while building it:
    - The title hero is dark in both themes, so artwork and the title over it look the same. The right-hand action column of the classic layout is kept for M4's tracking actions; until then the main column takes the width, with no buttons that do nothing.
    - Specials are listed last in the season picker, as on Trakt. Search results don't preload on hover, since opening a title fetches and stores it.
    - About doesn't show the version yet: no endpoint returns it.
