# M2: Auth — historical decisions and implementation notes

This preserves the milestone notes as recorded before they were moved out of the plan. Their branch and review statuses are historical; see the [rewrite plan](../rewrite-plan.md) for current status.

## Original scope and completion criterion

- Tables: sign-in columns on `users`, `sessions`, `api_tokens`. (`user_settings` moved to M4.)
- First-run setup, login, logout, sessions, CSRF check, login rate limit.
- Admin user management, API tokens.
- Svelte `/setup`, `/login`, and an authenticated layout.
- **Done when:** a fresh instance walks through setup and the dashboard is only reachable when signed in.

## Historical notes

- **Status: built, in review** (PRs #14–#19, stacked; each is retargeted to `main` after the one below it merges; mark this done when the last one merges), in six slices: (1) schema and the `internal/auth` service (passwords, setup, login, sessions, rate limiter); (2) the HTTP endpoints, session cookie, and CSRF; (3) admin user management and password changes; (4) API tokens; (5) the SPA's `/setup`, `/login`, and signed-in layout; (6) settings pages for passwords, tokens, and users.
  - Confirmed by the maintainer (2026-10-26): the password, session-renewal, login-limit, and no-sub-path choices below.
  - Passwords: argon2id with RFC 9106's memory-constrained parameters (64 MiB, 3 passes, 4 lanes), stored in PHC format so the cost can change later. At most two hashes run at once, bounding memory on small machines. At least 8 characters, at most 256 bytes; no composition rules.
  - A login for an unknown user is checked against a dummy hash with the same cost, so response time doesn't reveal which usernames exist.
  - Sessions renew their 30-day expiry at most once a day, so most requests don't write. Expired sessions were deleted at login until M3 slice 1 moved that cleanup into an hourly job.
  - Slice 2 endpoints: `GET /api/v1/auth/session` (whether setup is needed, and the signed-in user; never 401, so the SPA can call it on startup), `POST /api/v1/auth/setup`, `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`. The session cookie is `watcht_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` when the request came over HTTPS (directly, via a trusted proxy's `X-Forwarded-Proto`, or with an `https` `WATCHT_BASE_URL`).
  - Login limit: 10 attempts per client IP (per /64 for IPv6), then one a minute; successful logins don't count. The client IP comes from `X-Forwarded-For` only when the peer is a trusted proxy, read from the right. A login waits at most 10 seconds for a password-hashing slot, then gets 503.
  - Slice 3 endpoints, all needing a browser session (never an API token): `PUT /api/v1/me/password` (current password required; ends the user's other sessions; limited like logins, per account), and for admins `GET`/`POST /api/v1/users`, `DELETE /api/v1/users/{id}`, and `PUT /api/v1/users/{id}/password` (a reset for someone who forgot theirs; ends all their sessions). Admins can't delete their own account, so one admin always remains, and reset their own password through `/me/password`. The admin flag is set when an account is created; changing it later isn't built yet.
  - Slice 4: API tokens (`wt_` plus 32 random bytes, base64url; only the SHA-256 is stored), named per user, shown once, revocable. `GET /api/v1/me` is the first endpoint for scripts: it takes a session cookie or `Authorization: Bearer wt_...`. Only a header of that form makes a request a token request, and then the cookie is ignored, so a bad token is a 401, never a fallback; any other `Authorization` header (a reverse proxy's Basic auth, an oauth2-proxy JWT) is ignored and the cookie decides (maintainer decision, 2026-10-26). `GET`/`POST /api/v1/tokens` and `DELETE /api/v1/tokens/{id}` need a browser session (a token gets 403 `session_required`), so a token can't mint more tokens. Creating a token also needs the current password, limited per account together with password changes, because a token outlives logout and password changes: someone at an unlocked browser mustn't be able to mint one (maintainer decision, 2026-10-26). Deleting an account revokes its tokens; a password change or reset doesn't (they're separate credentials, revoked one by one, so a forgotten password doesn't break a media-server integration; confirmed by the maintainer, 2026-10-26). The webhook token in a URL comes with M7.
  - Slice 5 (SPA): every navigation loads `GET /api/v1/auth/session` in the root layout and redirects: to `/setup` on a fresh instance, to `/login?next=<page>` when signed out, and away from `/login` and `/setup` when signed in. After signing in, `next` is followed only if it's a path on this site. The server enforces access on every API call; the redirects only keep the UI honest. An API call that finds the session gone (401 `unauthenticated`) re-runs the session check, which leads to `/login`.
  - Slice 6 (SPA): `/settings` (change your password; create, list, and revoke API tokens, with the secret shown once) and `/admin/users` (admins add users, reset passwords, delete accounts; non-admins are redirected to `/settings`). The header links to Settings, and to Users for admins. Dates show in UTC until M4 adds the time zone setting.
  - Left for later: changing the admin flag after an account is created; a sessions list ("signed in on these devices"); token scopes and last-used times (M7).
  - For the self-hosting docs (M6): set `WATCHT_TRUSTED_PROXIES` to the proxy's own address only, not a whole Docker or LAN range that also holds clients, or those clients can choose their IP. Without it, every client behind the proxy shares one login limit, so one person guessing passwords locks the household out for a while; watcht logs a warning the first time it sees `X-Forwarded-For` from an untrusted peer. `/0` ranges are refused. When TLS ends at the proxy, watcht can't see the original scheme itself: it learns it either from the proxy's `X-Forwarded-Proto` (believed only from trusted proxies) or from an `https` `WATCHT_BASE_URL`. The docs recommend the base URL, which needs no headers and can't be spoofed; a proxy that sends no `X-Forwarded-Proto` with no base URL set means cookies without `Secure`, so watcht warns at startup when trusted proxies are set without an `https` base URL. With an `https` `WATCHT_BASE_URL` the cookie is always `Secure`, so signing in over plain `http://<lan-ip>` won't stick. Cookies aren't isolated by port, so other apps on the same host name can see `watcht_session`; a host name of its own is safer.
